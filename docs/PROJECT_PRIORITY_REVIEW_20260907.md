# Pi_zaya 功能、效果与计划复审（2026-09-07）

状态：审阅结论与建议；本文不代表下述优化已实施，也不替代原计划的历史验收记录。

## 结论

产品边界和基本技术栈适合当前目标。近期文献篮数据安全工作有实际价值，但当前
优先级表已经过度集中于局部生命周期和文件拆分。应当先收口已复现的数据覆盖问题，
随后把主要投入转向真实阅读问题的检索、上下文选择、回答支持和原文定位。

无需重写产品或更换 FastAPI、React、SQLite。需要调整的是检索范围的传递方式、
证据处理的责任边界，以及以用户任务结果为核心的实施计划。

## 功能划分是否合适

| 功能域 | 判断 | 近期方向 |
|---|---|---|
| 文库导入、转换、索引与恢复 | 核心必要能力；已有质量门禁和定向修复 | 以真实任务中的坏页、缺表、定位失败决定修复投入 |
| 库内找证据、本文问答、文献篮内比较 | 应成为优化主线 | 先解决召回范围与证据进入最终上下文的损耗，再改排序策略 |
| 引用卡片、阅读器、精确定位 | 产品核心价值；不能只检查链接可点击 | 检查实际落点是否支持该句结论，以及是否保留原文上下文 |
| 文献篮、摘录和阅读笔记 | 合理且必要；数据安全必须优先 | 收口并发覆盖，随后优化收集、返回原文、继续提问的完整流程 |
| 网页/模型知识补充 | 用户已明确要求保留选择，当前独立选择方向合理 | 检查触发条件、来源披露及失败处理，避免错误召回触发不必要补充 |

| 可观测性与架构治理 | 必要支撑；目前基础已经较丰富 | 用于定位耗时和证据丢失，避免持续增加没有决策用途的仪表和协议 |

研究笔记及其导出继续服务于保存摘录、批注、来源和阅读进度。没有理由恢复写作、
润色或投稿准备方向，也没有必要为了功能完整而重新开放隐藏工作区。

## 直接影响排序的发现

### 1. 文献篮并发覆盖是真问题，仍应最先收口

真实 `ChatStore` 使用临时 SQLite 的复现：两个读取者同时持有 `[A]`，先后提交
`[A,B]` 与 `[A,C]`，保存均成功，版本依次增长到 2 和 3，最终仅剩 `[A,C]`，B 丢失。

[`save_citation_shelf`](../kb/chat_store.py) 的 revision 是结果版本，保存接口没有
expected revision 前置条件；事务保证单次写入完整，不能识别旧快照覆盖。
[`citeShelfSaveQueue`](../web/src/components/chat/citeShelfSaveQueue.ts) 只在同一浏览器
document 内排序。当前计划把多窗口列为下一步是正确的，但它应是有完成条件的修复切片。

建议先做真实 API/SQLite 的旧版本拒绝或等价冲突保护，结合操作意图重放、明确清空语义、
请求重复/结果未知处理。验收至少覆盖双窗口新增、删除与新增交错、清空后新增、未完成
写入时重启、旧客户端/其他写入入口。具体协议根据复现选择，不预设需要分布式系统。

### 2. dense 范围过滤存在已复现的召回损耗

[`local_retrieval_selector.py`](../kb/local_retrieval_selector.py) 存在两层限制：

- 允许来源从当前 sparse 命中中推导，没有显式接收用户选中的完整来源集合。注入同一
  论文的有效 dense 候选而 sparse 为空时，结果仍为空，模式却记录为 `hybrid_local`。
- `_SourceFilteredRetriever` 先调用全局 dense top 40，再过滤允许来源。相同的范围内
  候选在全局第 1 名时能补入，第 41 名时完全丢失，即使前 40 条全在范围外。

本轮是实际选择器的确定性复现，证明该边界的行为；没有声称测出了它在用户问题中的
发生比例。产品仍有其他结构化与稀疏补救路径，这些复现也不等于所有问题都会失败。

建议显式传递用户选中的来源集合，在允许范围内计算/筛选 dense 候选后再取 top K，
避免把 sparse 结果当成用户授权范围。新增结果仍需遵守质量排除、来源和定位契约。
当前全库 BM25 边界继续依据既有评测保留，范围修复不自动授权全库 dense。

### 3. 已证明候选召回有改善，但最终回答收益还需测量

已有 [12 条 fresh scoped 报告](retrieval_scoped_fresh_e5_v1.json) 中 Recall@10 从
0.541667 增至 0.666667，提升 12.5 个百分点，足以支持保留显式可选的本地语义路径。
但它是小型、指定范围的候选召回评测，不是整库或最终回答正确率。

[18 条当前领域报告](retrieval_product_e5_user_journey_v1.json) 中 scoped Recall@10
仅从 0.231481 增至 0.259259；全库没有召回收益且错误来源增加，原来的全库拒绝结论合理。

产品采用保护 sparse 前五、补入有限 dense 尾部的策略。
[`task_runtime.py`](../kb/task_runtime.py) 后续仍经过章节/文档聚合、来源选择和生成
上下文裁剪。因此需要跟踪 dense 新证据是否进入最终上下文、被答案正确使用、能否定位。
不能仅依据 top-10 指标就宣称用户的答案已经改善，也不能未测量就断言尾部证据全被丢掉。

### 4. 回归合同与语义真实性仍有明显距离

本轮运行 `python tools/research_qa/run_claim_verifier_baseline.py --validate-only`
通过，确认现有 [24 条诊断集](claim_entailment_lexical_baseline_v1.json) 结果仍是：
支持判断准确率 54.17%，8 条矛盾样本中 4 条被错误判为支持。该结果不代表实际问答
有 50% 错误，它表明词项重叠不能充分验证结论方向。

[78 条既有问答结果](research_qa_quality_outcomes_v1.json) 保留了真实运行和来源约束
证据，但其中 correctness 包含预期词项/直接回答检查，矛盾边界只有 4 条覆盖；100%
合同通过不能作为开放问题的语义正确率。既有 NLI 小样本候选有改善，但仍有误判，不能
仅凭该 24 条样本直接启用新的生产判定模型。

近期应扩大对否定、数值、单位、比较方向、适用条件和证据缺失的测试，针对最终回答
逐句回到来源核对。自动核验失败时由系统补检索、缩小或移除不支持的结论，并保留
可用证据；不增加要求用户修复内部核验状态的流程。

建议保留原日志及冻结评测记录，增加一份短的当前路线图，作为执行状态唯一入口：

1. 产品边界、当前用户可见功能及版本/工作树状态。
2. 最多三个当前目标，每项写明用户问题、证据、验收标准和完成条件。
3. 效果评分表：候选召回、最终上下文证据覆盖、回答支持、准确定位、完成任务耗时。
4. 之后再做和暂缓事项；历史实验报告通过链接访问。

冻结测试集与保留失败记录继续执行，但每次小修复不必再生成多层计划编号和独立

既有全部质量门禁保持；定向检查服务迭代，完整集成/发布门禁仍按原要求执行。

## 建议的新优先级

| 顺序 | 工作 | 完成条件 |
|---|---|---|
| P0 | 收口文献篮真实并发与重启覆盖 | 真实 API/SQLite 下已复现的旧快照覆盖受保护；自动合并/恢复有明确语义，相关写入入口一起验证 |
| P1-A | 修复选定范围 dense 召回，建立当前端到端效果基线 | 覆盖 sparse 零命中、范围内候选在全库 top K 外、文献篮多来源；按最终上下文及回答收益判定改善 |
| P1-B | 回答证据支持与否定/数字/条件核验 | 真实问题中的错误支持、错误拒绝及修复结果逐项可复核；不把新模型分数当事实真值 |
| P1-C | 阅读流程、转换/定位质量与耗时 | 从真实任务失败中选主要问题；记录首次看到有效证据、引用可定位、回到原阅读位置的成功率和 p50/p95 |
| P1-D | 收敛当前状态文档并形成可审阅的集成里程碑 | 当前路线图、README、仪表盘与实际可见功能一致；工作树变更被清点，不自动提交/发布 |
| P2 | 在上述修复边界内做架构拆分 | 抽出有单一职责与类型合同的模块，减少重复决策与跨层依赖，保护文件预算不增长 |
| 暂缓 | 全库 dense 推广、新 cross-encoder、云 embedding、新隐藏工作区功能、进一步扩展观测基础设施 | 仅在明确的效果/规模/用户需求证据出现后重新排序 |

P1-A 的基线可先选 24–36 个真实库内阅读问题，覆盖机制、实验数值、否定/限制、
多论文比较、来源追问和无证据问题；这是建议起始规模，不是统计充分性的声明。
保留未参与调优的来源/问题切分，复用现有标签与工具；由自动化执行并核对来源，
不安排用户逐项手工验收。工具或模型评审有分歧时保留为评测不确定性。

等待已发布用户的 opt-in 数据只适用于现场采用率、设备兼容性和真实分布验证。
库内真实论文、隔离环境和已有模型配置足以开展当前效果诊断，不应据此暂停 P1。

## 架构框架建议

保留模块化单体与当前栈，将边界逐步收敛为：

`明确来源范围 → 候选召回/融合 → 证据选择 → 结论与证据绑定 → 支持/定位核对 → 展示`

- 来源范围作为显式输入贯穿检索，不由召回结果反推。
- 查询、融合和上下文选择各自拥有清晰输入输出，能定位“候选找到了但生成没用上”。
- 原文片段、来源、页码/锚点、主张支持与来源质量具有规范数据合同。
- 展示层主要投影合同；语义修复收敛到明确的后端责任边界，保留必要的 UI 防御检查。
- 存储写入统一冲突语义；后台状态和前端状态不重复拥有事实判定。

架构预算本轮通过，但 `chat_render.py` 17,380 行、`reference_ui.py` 11,208 行、
`task_runtime.py` 10,504 行仍显示核心责任集中。前端拆分已经有收益，后续应随检索、
证据绑定、核验这些实质变化移动责任；行数下降只作约束，不作为主要产品绩效。

最终判断：上一轮提出的“先查真实并发覆盖”保留；其后的主线应调整为检索和最终
回答效果。当前技术栈可继续，当前长计划需要整理成可执行的产品路线图。
